# 长期记忆系统（longterm-memory）

**记忆不靠对话历史，靠文件。** 对话是工作内存（贵、短、会丢），文件是长期记忆（跨会话、跨月、跨年）。

## 四层结构

| 层 | 目录 | 作用 | 何时读 |
| --- | --- | --- | --- |
| T1 | `T1-交接/` | 冷启动简报：进度 + 活跃问题 + 用户习惯 + AI 踩坑 | **每次会话开头读一次**（唯一常驻上下文） |
| T2 | `T2-全日志/` | 原始会话存档，一周一文件 | **不主动读**，只在 T3 查不到时兜底 |
| T3 | `T3-分类整理/` | 结构化知识：`大类/模块/问题点` | **检索命中才读**，不通读 |
| T4 | `T4-项目/` | 实际代码与资源 | 按需读具体文件 |

T2 是冷存储，T3 是热缓存，T1 是寄存器。

> 目录命名有两套，工具自动识别，不要手改：`T1-交接/`（本技能默认）与 `T1-交接文件夹/`（DSH 插件命名）。
> 同一项目四个宿主共用同一份记忆，标记文件 `.longterm-memory.json` 与 `.dsh-longterm.json`。

## 怎么调用工具（两条路，按当前环境二选一）

**路 A：有 MCP 工具就直接用**（工具名见下）。装了 `longterm-memory` MCP 服务器的宿主里，这些工具已在工具列表里。

**路 B：没有 MCP 就用本技能自带的 CLI**（零依赖，只要有 Node ≥ 20）：

```bash
node <skill_dir>/scripts/ltm.mjs init   "<项目根>"              # 建骨架
node <skill_dir>/scripts/ltm.mjs brief  --root "<项目根>"       # 读简报
node <skill_dir>/scripts/ltm.mjs search "用户的原话" --root "<项目根>"
node <skill_dir>/scripts/ltm.mjs slice  --file "T3-分类整理/..." --heading "某标题" --root "<项目根>"
node <skill_dir>/scripts/ltm.mjs write  --title "问题点" --category "修复bug/模块" --content "..." --root "<项目根>"
node <skill_dir>/scripts/ltm.mjs log    --content "本轮原始记录" --root "<项目根>"
node <skill_dir>/scripts/ltm.mjs doctor --root "<项目根>"        # 自检
```

`<skill_dir>` 就是本 SKILL.md 所在目录。CLI 找不到项目根时会报错并提示三选一
（在项目根 init / 传 `--root` / 设 `LTM_PROJECT_ROOT`）。

| 目的 | MCP 工具名 | DSH 里的别名 | CLI 子命令 |
| --- | --- | --- | --- |
| 建骨架 | `memory_init` | — | `init` |
| 收养已有项目 | `memory_adopt` | — | `adopt` |
| 读简报 | `memory_brief` | `memory_handoff` | `brief` |
| 看有哪些记忆 | `memory_index` | `memory_list` | `index` |
| 检索 | `memory_search` | — | `search` |
| 取某一段 | `memory_slice` | `memory_read` | `slice` |
| 写入 T3 | `memory_write` | — | `write` |
| 追加 T2 | `memory_log` | — | `log` |
| 自检 | `memory_doctor` / `memory_status` | — | `doctor` / `status` |

## 会话开始（必做）

1. 读简报（`memory_brief` / `brief`）——取代通读任何文件，这是唯一的常驻上下文。
2. 从简报里拿到「当前活跃问题」和「下一步」，直接接上进度，不要重新问一遍。
3. **不要**为了了解项目去读整个 T2/T3；需要细节走下一节。

若简报为空模板或报「没有 T1 交接文件」：说明项目还没接入。先 `init`（或 `memory_init`），
再把已知的项目状态写进 `T1-交接/项目进度交接.md`。

## 动手前（必做）

改代码 / 加功能 / 排查问题之前先检索：

- 用**用户的原话**当关键词（中文按单字+双字建索引，口语也能命中），不要先翻译成术语；
- 默认只搜 T1+T3（`scope=hot`）；明确没有时再用 `scope=all` 回查 T2；
- 命中后用 `slice` 取那一节全文，**不要**把整个文件拉进上下文；
- **命中历史同类修复**：先按历史结论处理，不要重新发明方案；若历史方案已失效，
  明确说明「旧方案 X 为什么不再适用」；
- **搜不到**：直接说「记忆里没有相关记录」，然后基于当前代码判断。
  **禁止**编造一条看起来合理的历史修复记录。

## 会话收尾（必做）

不归档等于这次会话白干。

1. **写 T3**：`memory_write` / `write`。大类只取 `修复bug` / `新功能` / `疑问咨询` / `回顾重构`，
   二级是模块，三级是问题点（例：`修复bug/游戏机制/NPC相关问题`）。
   正文固定五段：**现象 / 根因 / 改了什么 / 怎么验证 / 遗留风险**。
   同一个问题反复出现时**续写同一个文件**（工具自动编「第 N 条记录」），不要新建文件。
2. **追加 T2**：`memory_log` / `log`，写本轮做了什么、改了哪些文件、结论是什么。
3. **更新 T1**：
   - `T1-交接/项目进度交接.md`：只留「当前状态 / 下一步 / 关键约束」，≤200 行；
   - `T1-交接/当前活跃问题.md`：只留正在处理的，已解决的移出。
4. **踩坑与偏好**：用户纠正过你、或同一个错误犯了第二次 → 追加
   `T1-交接/交接文档/AI经常踩的坑.md`，格式：现象 → 根因 → **硬规则**。
   用户表达了新的输出偏好 → 更新 `用户习惯.md`。

## 硬规则

- T1 是常驻上下文，**每多一行都在每次会话重复付费**。写之前先想「这句有必要天天读吗」。
- `AI经常踩的坑.md` 价值最高也最容易漏：同一个坑犯第二次就必须写。
- 检索不到不等于没有：先换用户的另一个说法再试一次，然后才下结论。
- 不要替用户决定归档位置；分类拿不准就放 `其他/`。

## 反模式（不要做）

- ❌ 为了「了解项目」把 T2/T3 整个读一遍 —— token 黑洞，还引入无关上下文导致幻觉。
- ❌ 每次会话都在 T3 新建文件记录同一个问题 —— 破坏「同一问题累加」的设计。
- ❌ 把进度写在回复里而不写进 T1 —— 下次会话读不到。
- ❌ 记忆里没有却说「之前好像修过」—— 查不到就是查不到。
- ❌ 把 T1 写成流水账 —— T1 是简报，流水账归 T2。
